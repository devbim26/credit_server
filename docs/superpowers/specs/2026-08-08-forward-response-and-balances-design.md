# Дизайн: приём ответа внешнего сервера + реестр балансов

**Дата:** 2026-08-08
**Статус:** одобрен пользователем

## Контекст

Сегодня сервер списания кредитов только отправляет сводки об использовании на
внешний («другой») сервер и фиксирует успех/провал (`forward_log.status`,
`http_status`). Тело ответа внешнего сервера **сейчас выбрасывается**.

Нужно:
1. Принимать от внешнего сервера **ответ** — дата/время, email, сколько списано
   (`charged`), и **остаток кредитов пользователя** (`balance`).
2. Хранить эти данные и показывать в GUI.
3. Вести **реестр балансов** — последний известный остаток по каждому email.

Внешний сервер разрабатывает разработчик пользователя — формат ответа мы
**определяем** (фиксированный контракт), разработчик его реализует.

## Контракт ответа внешнего сервера

Наш сервер отправляет (без изменений):

```
POST {FORWARD_URL}
Authorization: Bearer {FORWARD_API_KEY}   (если задан)
Content-Type: application/json

{
  "email": "user@example.com",
  "function": "...",
  "model": "...",
  "timestamp": "2026-08-08T13:59:41+00:00",
  "tokens": 1234,
  "prompt_tokens": 1200,      // опционально
  "completion_tokens": 300,   // опционально
  "cost_usd": 0.00123         // опционально
}
```

Внешний сервер отвечает **`200 OK`** (`2xx`) с фиксированным JSON:

```json
{
  "datetime": "2026-08-08T13:59:41+00:00",
  "email": "user@example.com",
  "charged": 50,
  "balance": 950
}
```

| Поле | Тип | Назначение |
|---|---|---|
| `datetime` | string (ISO 8601) \| null | Дата/время списания на стороне внешней системы |
| `email` | string \| null | Для сверки (от кого списали) |
| `charged` | number \| null | Сколько кредитов списано внешней системой |
| `balance` | number \| null | Остаток кредитов пользователя после списания |

**Правила разбора:**
- Дополнительные поля игнорируются (контракт расширяется向后-совместимо).
- Отсутствующие/`null` поля → сохраняются как `NULL` в БД.
- `balance: 0` — **валидное** значение (обновляем реестр).
- Любой статус `≥ 400` → `failed` (без изменений в логике).
- Статус `2xx`, но тело не JSON или пустое → `ok`, поля ответа = `NULL`
  (сервер не падает).
- Реестр балансов обновляется **только** при валидном `balance` (не null).

> «Кредиты» в ответе — валюта внешнего биллинга. Внутренние кредиты
> (`usage_records.credits`) считаются как раньше. `charged` может не совпадать с
> ними — это полезно для сверки расхождений между системами.

## Модель данных

### `forward_log` — новые nullable-колонки (миграция)

Через существующий механизм миграции (`MIGRATION_COLUMNS`):

| Колонка | Тип | Назначение |
|---|---|---|
| `resp_datetime` | TEXT | `datetime` из ответа |
| `resp_email` | TEXT | `email` из ответа (сверка) |
| `resp_charged` | REAL | `charged` из ответа |
| `resp_balance` | REAL | `balance` из ответа |
| `resp_raw` | TEXT | сырой JSON-ответ, обрезанный до ~1 КБ (аудит/дебаг) |

### Новая таблица `user_balances` — реестр

```sql
CREATE TABLE IF NOT EXISTS user_balances (
    email        TEXT PRIMARY KEY,
    balance      REAL,           -- последний известный остаток
    last_charged REAL,           -- последнее списание
    last_updated TEXT,           -- datetime из ответа внешнего сервера
    forward_id   INTEGER,        -- какая запись forward_log обновила баланс
    updated_at   TEXT NOT NULL   -- локальное время последнего upsert (UTC)
);
```

`upsert` по `email` при каждом успешном ответе с валидным `balance`.

## Поток данных

```
сниппет → POST /api/usage → usage_records → forward_log(pending)
                                              ↓ forwarder (POST)
                                       [внешний сервер]
                                              ↓ 200 {datetime, email, charged, balance}
                          forward_log(ok, resp_*)  →  user_balances (upsert по email)
                                              ↓
                                  GUI: «Пересылка» + «Балансы»
```

## Обработка ошибок / крайние случаи

- Не-JSON / пустое `2xx`-тело → `ok`, `resp_*` = NULL (сервер не падает).
- Отсутствует `balance` (null/нет ключа) → `forward_log` обновляем, реестр **не трогаем**.
- `balance: 0` → валидно, обновляем реестр.
- `failed`/таймаут/сетевая ошибка → `failed` как сегодня, реестр не трогаем.
- `email` в ответе отсутствует → для `upsert_balance` берём `email` из самой записи
  `usage_records` (надёжно: наш сервер знает, кому шлёт).
- `datetime` невалиден/отсутствует → сохраняем NULL; в `user_balances.last_updated`
  NULL, в `updated_at` — локальное время upsert.

## Тестирование

E2E через существующий `test_pipe/`:
1. Запустить `mock_external_server.py` (новый контракт) + `fake_openrouter_server.py`.
2. Отправить запрос через тестовый pipe → запись появляется в `forward_log` со
   статусом `ok` и заполненными `resp_charged`/`resp_balance`.
3. Проверить `GET /api/balances` — баланс email обновлён (1000 − charged).
4. `GET /toggle-fail` → следующий запрос → `failed`; реестр не изменился.
5. `GET /toggle-fail` → `POST /api/retry-failed` → запись доходит, баланс обновлён.

## Что НЕ входит (scope)

- Нет второго направления (внешний → мы): только ответ на наш POST.
- Нет пополнений/корректировок как отдельного типа операции — только `charged`
  из ответа на списание.
- Нет авторизации по `resp_email` (это справочное поле для сверки).
